Module Sarek_policy

One typed store for every precision grant and consent (specs/optimisation-policy.md).

The program states, once, which deviations from the interpreter's result it accepts (deviation) and which rewrites of its own code it allows (consent); this module records those statements and answers "is this grant in force, and why". It sits in the lowest layer (sarek_ir, no dependencies) so that code generation, the capability gate and the launch path can all ask it.

What it is not. It is not a switch board: nothing here turns an optimisation on or off, and no environment variable grants anything (SPOC and Sarek environment variables only restrict). It does not change what any caller computes: Sarek_coopmat.accept_relaxed_accumulation and the other opt-ins are thin wrappers over grant, with the same refusals and the same messages as before it existed.

Who consults which scope (milestone M1). A decision point that knows the kernel it is deciding for reads reason with ~kernel, so a Kernel-scoped grant is honoured there; today that is the f32 to f16 narrowing in the CUDA-C generator only. The coopmat verdicts and the matrix rewrite read the process scope. From M2 every decision point consults the scope of its kernel through budget. A Kernel-scoped coopmat grant is accepted and recorded now, and is read from M2.

Vocabulary

type operand_precision =
  1. | Operands_f16
  2. | Operands_bf16
  3. | Operands_bf16x3

The operand type a float32 matrix product is rounded to before it runs on matrix units. Operands_bf16x3 splits each operand into three bfloat16 terms for near-float32 accuracy. Re-exported, with its constructors, by Sarek_coopmat.

type deviation =
  1. | Accumulation_order
    (*

    the hardware chooses the order of the additions (Sarek_coopmat.accept_relaxed_accumulation)

    *)
  2. | Operand_rounding of operand_precision
    (*

    float32 operands are rounded to a narrower type on load (Sarek_coopmat.accept_operand_rounding)

    *)
  3. | Single_rounding
    (*

    an f32 to f16 narrowing may round once where the interpreter rounds twice (Sarek_f16_policy.accept_single_rounding)

    *)
  4. | Cross_kernel_contraction
    (*

    a device compiler may contract a multiply of one fused kernel with an add of the next. Grantable now; read by epilogue fusion from M2.

    *)

A named way a result may differ from the interpreter's. Each carries its own documented bound where one exists; there is no common numeric scale.

type consent =
  1. | Automatic_float_rewrite
    (*

    the automatic float matrix rewrite of Execute.run_vectors (Sarek_coopmat.accept_automatic_float_rewrite)

    *)

A permission to rewrite the program's own code, separate from accepting any accuracy deviation: granting one never grants the other.

type grant =
  1. | Deviation of deviation
  2. | Consent of consent
type optimisation =
  1. | Launch_window
  2. | Epilogue_fusion
  3. | Matrix_rewrite
  4. | Narrowing_proof
  5. | Auto_unroll

Every transformation a policy decision can apply to a launch. Vocabulary for the explain report; the decision points are wired to it from M2.

type scope =
  1. | Process
  2. | Kernel of string

Where a grant applies. Kernel name matches Sarek_ir_types.kernel.kern_name exactly; a kernel built by a fusion pass has the fused name, not those of its parts.

type refusal =
  1. | Blank_reason
  2. | Default_kernel_name

Why grant (or Budget.add) refused. Default_kernel_name: Kernel "sarek_kern", the name every unnamed [%kernel] gets, would cover all of them.

type evidence =
  1. | Proof of string
  2. | Granted of string
  3. | Exact_by_construction

What justifies an applied optimisation, for the explain report.

type decision =
  1. | Applied of evidence
  2. | Refused of string

The outcome of one decision point, for the explain report.

val grant_name : grant -> string

Stable names, used in reports and in cache keys: "accumulation-order", "operand-rounding-f16", "operand-rounding-bf16", "operand-rounding-bf16x3", "single-rounding", "cross-kernel-contraction", "automatic-float-rewrite".

val optimisation_name : optimisation -> string

"window", "epilogue", "matrix", "narrowing-proof", "unroll".

val all_grants : grant list

The seven grants, in the order Budget.grants lists them.

Budgets

module type BUDGET = sig ... end
module Budget : BUDGET

The process-wide store

val grant : scope -> grant -> reason:string -> (unit, refusal) Stdlib.result

grant scope g ~reason records that the program accepts g for scope. Process-wide and one-way: there is no withdrawal, so a check that passed (and that a caller memoised) can never become stale. Thread-safe (an Atomic updated by compare-and-set). The first non-empty reason per (scope, g) is kept; later calls for the same pair are no-ops. A blank reason is Error Blank_reason and Kernel "sarek_kern" is Error Default_kernel_name; a refusal records nothing.

val reason : ?kernel:string -> grant -> string option

reason ?kernel g: with ~kernel, that kernel's own grant first, then the process grant; without, the process grant only. None when not granted.

val budget : kernels:string list -> Budget.t

budget ~kernels: the budget of a launch whose kernel is built from kernels. For each kernel, its process grants plus its own; the result is the Budget.meet over the kernels, so a grant held by one member only is absent. [] gives the process grants only. Reads one consistent snapshot of the store.

val refusal_message : refusal -> string

The sentence for a refusal of grant.
