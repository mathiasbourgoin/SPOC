val exec_stmt : Sarek_ir_interp_value.thread_state -> Sarek_ir_interp_value.env -> Sarek_ir_types.stmt -> unit

Cooperative matrix — backlog-62 slice 3

The interpreter is the ORACLE every backend is checked against, so this is not a courtesy implementation: test_coopmat_integer_e2e (GLSL) and test_coopmat_hip_e2e (HIP) compare the backends' output against these numbers bit for bit, and a skip here would let a coopmat kernel "agree" with an interpreter that never computed the product.

Every invocation holds the whole matrix and performs the whole operation; see Sarek_ir_interp_value.env.coopmats for why that is exact rather than approximate.

Integer configurations are a strict oracle: the specification states integer accumulation is exact at the precision of the result type.

The one float configuration with a derived bound — f16 * f16 + f32 -> f32 — is evaluated only after Sarek_coopmat.accept_relaxed_accumulation, and in ONE FIXED ORDER: acc := C[m][n], then for k = 0 .. K-1, acc := fl32 (acc + A[m][k] * B[k][n]). The product of two binary16 values is exact in binary32, so the only rounding is the addition's. The hardware chooses its own order, so this is one admissible member of the bounded set (docs/design/f16-relaxed-accuracy.md §5.2), not a value a device must equal; tests compare both against the exact result under the bound. Every other float configuration is refused (Sarek_coopmat.policy_verdict).

val coopmat_component : Sarek_coopmat_types.component_type -> Sarek_ir_interp_value.value -> Sarek_ir_interp_value.value

Convert a buffer element to the declared component type.

For the 8-bit operand types this is what makes the interpreter a faithful oracle rather than merely a plausible one: a value loaded into a u8 fragment from a buffer holding 300 is 44 on the device, and an oracle that kept 300 would disagree with correct hardware. For f16 it is the round-to-nearest-even narrowing the device performs (the identity on a float16 buffer).
